# Where was I?

Answer "where was I / what's done / what's pending" from the **records** — `BUILD_STATE.md`,
`TRACKER.md`, git and CI — not from source files and not from memory.

**The deliverable is a document, not terminal output.** The terminal gets a six-line
receipt. The answer itself is written to `docs/STATUS.md`: diagrammed, addressable by id,
and accumulating across runs so progress is visible over time.

Target: a complete, honest status in under ~8 tool calls, no source files read.

---

## What the output IS

One file, `docs/STATUS.md`, containing these parts **in this order**. Every part appears on
every run; a part with nothing in it says so in one line rather than being dropped.

| # | Part | Form |
|---|---|---|
| 0 | Banner | Generated-file warning, source list, run timestamp |
| 1 | **Position** | 4-row table — where the build actually is right now |
| 2 | **Map** | mermaid `mindmap` — the whole state on one screen |
| 3 | **Order of play** | mermaid `flowchart` — what unblocks what |
| 4 | **Movement** | append-only run log + mermaid `timeline` of shipped work |
| 5 | **Open items** | one **W-block** card per item, sorted P0 → P3 |
| 6 | **Blocked on you** | table — human decisions, credentials, manual steps |
| 7 | **Asked earlier** | ledger — last session's questions and what came of them |
| 8 | **Stale records** | reconciliation table — where the docs contradict reality |
| 9 | **Answer key** | id → 3-6 word label |

If the repo has no `docs/`, create it. If the repo keeps top-level records only and has no
`docs/` convention at all, write `STATUS.md` at the repo root instead.

**Write the file. Never commit it.** A status answer that commits is a status answer that
changed the thing it was measuring.

### Part 0 — the banner, verbatim shape

    > **Generated by `/where-was-i` on <ISO date>. Do not hand-edit — the next run overwrites it.**
    > Sources: `TRACKER.md` · `BUILD_STATE.md` · `git log` · `gh run list` · live probes.
    > A problem still open is a `TRACKER.md` line. A decision made is a `BUILD_STATE.md` `D0NN`.
    > This file is neither — it is the view that reconciles them.

This banner is load-bearing in any repo that enumerates which file holds what. Without it
`docs/STATUS.md` becomes one more record to keep in sync, which is the exact failure those
conventions exist to prevent.

## Five non-negotiable rules

1. **The state docs lag reality.** A `BUILD_STATE.md` header, a "Next session" note or a
   `TRACKER.md` item saying *"fixed in code, not deployed"* was true when written and is
   routinely false now. Never repeat a doc's claim about deployment, verification or
   "pending" without checking it against `git log` and CI (step 3).
2. **Every open item carries a priority.** Items already in the tracker keep theirs;
   anything you surface that the tracker does not carry gets one **assigned by you**,
   marked `(assigned)`, using the rubric below.
3. **Every open topic carries a `#NN` id**, so the user can answer by id alone.
4. **Every open item carries a full W-block.** See below. An item whose *why* and *when*
   cannot be stated is an item that should not be on the list.
5. **Never invent what you said before.** A prior-session summary preserves the user's
   questions, rarely your answers. Where the answer is not preserved, infer the *outcome*
   from repo state and label it — never reconstruct dialogue.

## The W-block

Every open item is a card, not a table row. This is the part the user comes back for: it
must answer *why do this, why now, where does it happen, and who does it* without them
having to ask a follow-up.

    ### #01 · P1 · Short title `stable-id`

    | | |
    |---|---|
    | **What** | One sentence. The defect or the gap, not the fix. |
    | **Why** | The consequence. A number or a named risk, never an adjective. |
    | **When** | What makes it timely — the trigger, the deadline, or what must be true first. |
    | **Where** | The file, service, dashboard or sibling repo it touches. Specific enough to open. |
    | **Who** | `me` · `you` · `both` — and if `you`, exactly what is needed from them. |
    | **How** | One imperative clause. The next action, not a description of the problem. |
    | **Done when** | The observable that closes it. A header, a log line, a green run. |
    | **Progress** | `code – · dep – · ver –`, ticking each to `✓` as it lands. |
    | **First seen** | Date it entered the records · how many runs it has been open. |

**Why and When are the two that get faked.** Guard them:

- **Why** states the *consequence*, never a paraphrase of the item. *"No observability"* is
  the item; *"27% of traffic is unattributable until logs exist"* is the why. For done work
  it is what it bought, past tense, with the measured delta.
- **When** states what makes it *now* rather than later — a dependency that just cleared, a
  number trending the wrong way, a launch it gates, or plainly *"not urgent; do it when you
  next touch this file"*. "When" is not a restatement of the priority.

**Progress keeps three states distinct in one cell** — code written, deployed, verified.
They are three different things and collapsing them into one word is how items get called
done early.

## Diagrams

Mermaid, in fenced mermaid blocks — it renders on GitHub, in VS Code preview, and natively
in Claude artifacts, so the document is readable everywhere without a toolchain.

Three diagrams are **required**, because each answers a question a table cannot:

**1 · Map (`mindmap`)** — the whole state on one screen. Root is the repo. Branches are
Shipped / Open / Blocked / Deferred. Leaves carry the `#NN` id so the map is navigable.
Answers *"how much is there, and what shape is it in"*.

**2 · Order of play (`flowchart LR`)** — the dependency graph. An edge means *this must
land before that becomes possible*. Mark human-gated nodes distinctly. Answers *"what do I
do first"*, which a priority-sorted list cannot, because P2 items routinely unblock P1
items.

**3 · Movement (`timeline`)** — what shipped, by date, newest section last. Answers *"am I
actually moving"*, and it is what makes the document progressive rather than a snapshot.

Add a fourth, a small `flowchart TD`, **only** for an item whose next action is genuinely
conditional — *check the dashboard → exists? configure : accept the watch as the detector*.
A flowchart of a linear instruction is worse than the sentence it replaces.

Keep node labels short and put the detail in the cards. A diagram that repeats the tables
costs a screen and buys nothing.

**Mermaid syntax that bites:** parentheses, colons and commas inside a `mindmap` leaf break
the parse — write leaves as plain words, and quote any `flowchart` node text carrying
punctuation, as in `A["58% 404s, unattributed"]`. Percent signs are fine; a bare `(` is not.

## Progressive across runs

The file is rewritten each run, but three things accumulate so history survives:

- **§Movement** gains one row per run: date, what shipped since the last run, open count by
  priority. Never rewrite past rows — a row that turned out wrong gets a following row
  saying so.
- **Every card carries `First seen` and an age in runs.** An item open for nine runs is
  telling you something a priority label is not.
- **Resolved items move to a collapsed `<details>` block at the end of §Open items**, with
  the date and what closed them, so the document stays readable while the history stays.

Before writing, read the existing `docs/STATUS.md` if there is one — that is where
`First seen`, the age counts and the prior §Movement rows come from. Without that read the
document resets itself every run and stops being progressive.

## Ids

- Format `#01`, `#02`, … Two digits, one flat sequence across the document, assigned
  top-to-bottom in the order cards appear.
- **One id per topic, not per row.** A topic appearing in both §Open items and §Blocked on
  you keeps the *same* id in both places.
- Ids go only on things the user could **answer or dispatch**. §Position, §Movement and the
  resolved block get none.
- Where a durable tracker id exists (`workout-404-flood`), print it alongside. `#NN` is for
  typing; the tracker id is for resolving later.
- **Ids are document-scoped and renumbered on every run.** Say so under the answer key.

## Resolving a reply

When the user replies `#07 yes` / `#03 do it` / `#11 skip`:

1. Resolve each id against the **current `docs/STATUS.md`**, re-reading it if this session
   did not write it.
2. Echo the card title back in one short clause per id — *"#07 reconcile TRACKER.md — doing
   it"* — so a renumbering mistake surfaces before any edit rather than after.
3. If the id resolves to nothing, say so and ask. Never guess which card was meant.
4. Then act, in id order.

## Priority rubric

Use the repo's own rubric if it has one (Easeur repos define it at the top of
`TRACKER.md`). Otherwise, and for anything you assign yourself:

| Pri | Meaning |
|---|---|
| **P0** | Live site down, data loss, or a secret exposed. Drop everything. |
| **P1** | User-visible breakage, **or the product publicly claims something untrue**. |
| **P2** | Real risk or debt, not yet biting. Schedule it. |
| **P3** | Deferred nicety, or a decision that blocks nothing. Do when convenient. |

Two things people habitually under-rate:
- An overclaiming public stage, changelog or marketing line is **P1**, not cosmetic, in any
  repo whose premise is verifiable claims.
- Monitoring that silently under-reports is **P2**, because it converts every future outage
  into a late one.

## Steps

1. **Locate the records.** In an Easeur repo: `BUILD_STATE.md` and `TRACKER.md` at the repo
   root, plus `../CLAUDE.md` (already in context — the ecosystem map, the per-app stage
   table, **and a "Known discrepancies" list the per-repo tracker usually does not
   mirror**). Elsewhere use `TODO.md`, `CHANGELOG.md`, an issue tracker, or git alone.

2. **Read the open work first, state second.** Batch in one message:
   - `cat TRACKER.md` (or equivalent) — the pending list.
   - `git status --short`, `git log -12 --date=short --format='%h %ad %s'`,
     `wc -l BUILD_STATE.md`.
   - `grep -n '^### D' BUILD_STATE.md | tail -40` — the decision-log index.
   - `cat docs/STATUS.md` if it exists — the prior run, for `First seen` and §Movement.

   Do **not** `cat` a long `BUILD_STATE.md`. Read its "Current state" head (`sed -n '1,80p'`)
   and only the last 2-4 `D0NN` entries by line range. That is where the session actually
   stopped, and those entries hold the *why* for recent work — read them properly rather
   than skimming titles.

3. **Cross-check the docs against reality.** Batch:
   - `git log -3 --name-only` — what the last commits touched.
   - `gh run list --limit 8` — did the last push deploy, and did checks pass?
   - `gh issue list --state open --limit 5` — what the automation filed.
   - If a workflow watches production, pull the **report lines** out of the newest run
     rather than trusting green/red alone. A green run on a thin data window is not an
     all-clear — say so in §Position.
   - One cheap live probe (a `curl -I`) beats a paragraph of inference about whether a fix
     is really deployed. Take it whenever a tracker item claims "not deployed".

   Reconcile: an item the tracker calls "not deployed" that appears in a commit with a
   successful deploy run **has shipped**. Say so, and list the tracker line in §Stale
   records.

4. **Account for the tail of the last session.** Uncommitted work and discussion that
   produced no commit are both invisible to the records. If a prior-session summary is in
   context, walk its user messages **in order** and build §Asked earlier. For each
   question, find the outcome in the repo — a `D0NN`, a tracker line, a commit, a workflow
   — and if there is none, the answer never landed and the thread is open. Those rows are
   usually the real answer to "where was I".

5. **Write `docs/STATUS.md`.** Then print the terminal receipt below, and offer in **one
   line** to publish it as an artifact for a rendered, shareable version.

## The terminal receipt

Six lines, maximum. It is a receipt, not the report:

    docs/STATUS.md updated — 2026-09-06

    Position   7952e49 deployed OK · tree clean · watch red (1 finding)
    Shipped    3 fixes verified live since last run
    Open       2 P1 · 8 P2 · 5 P3 — 6 blocked on you
    Changed    #01 worsened (58% 404s), #11 unblocked
    Next       #02 is a one-line product decision and clears a P1

`Changed` is the line that earns the receipt: what moved since the last run. On a first run
it reads `first run — no prior document`.

## Common mistakes

| Mistake | Fix |
|---|---|
| Writing the full report to the terminal as well as the file | The receipt is six lines. The document is the answer. |
| A `Why` that restates the item | State the consequence with a number or a named risk. |
| A `When` that repeats the priority | "When" is the trigger or dependency, not the severity. |
| Regenerating the file without reading the old one | `First seen`, ages and §Movement all reset, and the document stops being progressive. |
| A mindmap that lists every item in full | Leaves carry id + 3 words. Detail lives in the cards. |
| Presenting a "Next session" note as current | Re-derive it from git and CI. |
| Committing the generated file | Write it and stop. The user commits. |

## Do not

- Read source files, run a build, or start fixing what you find. Read-only report.
- Spawn subagents. The whole point is that this is cheap.
- Leave an open item without a priority, an id, or a complete W-block; or an answered
  question without a source.
- Act on an id without echoing back what it resolves to.
